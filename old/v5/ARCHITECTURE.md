# HomeSense v5 — 架构决策记录

> 定位：**Agent 智能版的小爱同学** —— 一个家庭一个大脑。
> 本目录记录 v3 演进到 v5 的架构决策、目标模型与已达成共识，供后续实现参考。

- 状态：设计中（截至 2026-09-01）
- 关联：v3 当前实现见 `apps/web`；历史归档见 `old/`、`docs/v3/`

---

## 0. 一句话定位

HomeSense 不是通用聊天软件，是**家庭级智能体（家庭大脑）**：
像一个小米音响/小爱同学，全家共用一条上下文，聊天永不结束，
渠道（Web/飞书/音箱/微信）只是这个大脑的**耳朵和嘴**，不是会话边界。

## 1. 核心心智模型：租户 = 一个共享大脑

### ⚠️ 第一条铁律（无论如何不可打破）

> **GO 不是「网关」，它只是一个 agent 实例（工作区）。**
>
> 本仓库里那个 per-tenant 的 Go 进程（`v5/backend/pkg/channels/pico` 所在的进程，命令行 `picoclaw`）：
> 承载单个家庭的 agent 大脑、执行工具、读写它自己的工作区，**仅此而已**。
> 它不是一个「数据面前置」「计量层」「计费层」「超限拦截」等任何业务承载系统。
>
> - **一切业务逻辑（计费 / 钱包 / 单价 / 配额 / 用量账本 / 管控）都必须在云平台（Next.js 控制面）实现**，
>   不在 Go 进程里做任何钱的计算、不做任何商业判定。
> - Go 进程顶多记录**客观事实**（如真实 LLM token 用量），这是它干活时的副产物，不是计费任务；
>   它永远不参与费用换算、余额判断、超限决策。
> - 后续任何需求在「要不要往 Go 那边加东西」时，先回到这条铁律：
>   **能放云平台就绝不进 Go；Go 只做 agent 实例的本职。**

### ⚠️ 顶层分离（云平台 vs agent 实例）

```
云平台（Next.js 控制面）          = 唯一业务中心：租户/登录/模型源/计费/钱包/用量账本/配额
agent 实例（Go 进程，per-tenant） = 一个家庭的工作区：跑大脑、执行工具、报告真实 token 事实
```

### ⚠️ 数据存储铁律（平台数据 vs 用户数据）

| 数据 | 本质 | 存储 |
|---|---|---|
| 聊天历史 / 时间线（`pico_messages`） | **用户数据 = 用户个人财产** | per-tenant SQLite |
| token 用量（`pico_usage`）、钱包/账单/单价/配额 | **平台账本数据** | **PostgreSQL**（统一平台库） |

> SQLite **永远不存用量和钱**。用量/钱是平台级的，混进用户 SQLite 是错误架构。
> 完整方案见 `v5/docs/billing-postgresql-platform-db.md`。

```
家庭（tenant，一个大脑）
  ├─ 耳朵/嘴: Web 网页
  ├─ 耳朵/嘴: 飞书 bot / 群聊
  ├─ 耳朵/嘴: 音箱 / 家庭设备
  └─ 大脑: 共享上下文 + 无界时间线记忆（timeline）
```

### 1.1 绝对原则

| # | 原则 | 说明 |
|---|---|---|
| 1 | **全家一条上下文** | 家庭成员共享同一会话上下文；"爸说停空调，妈后来问安排"必须能接上话 |
| 2 | **渠道 = IO 路由** | Web/飞书/设备发进来的消息，都汇入同一个家庭大脑；不按渠道开独立上下文 |
| 3 | **账号 = 身份标签** | 多账号（爸/妈/娃）只区分"谁在说"，用于个性化称呼与权限；**不是**独立会话 |
| 4 | **聊天永不结束** | 不手动开/管理会话；会话自动存在，按对话上下文懒创建 |
| 5 | **租户 = 数据隔离边界** | 一个家庭一个租户，一个 per-tenant SQLite 库；动态伸缩目标仍成立 |

### 1.2 和通用 chat 客户端（pi / picoclaw）的本质区别

| | 通用 claw（pi / picoclaw） | HomeSense v5 |
|---|---|---|
| 会话模型 | 每对话一个 session（按渠道+conversationId） | 全家一个共享大脑 |
| 上下文 | 会话内上下文 | 共享上下文 + 无界 timeline |
| 渠道 | 各渠道独立 | 渠道只是一套 IO 口 |
| 多用户 | 每用户独立会话 | 同一大脑内的身份标签 |

> 结论：v5 有意**反着用** session 层的通用做法。picoclaw 可借鉴的部分只有它的**渠道层**
>（`pkg/channels/`，飞书/微信/Telegram/Discord 等），其 session 层与 v5 冲突。

## 1.5 执行端设计：云大脑 + 双执行端（盒子/手机）

**决策（2026-09-01）：大脑（认知/记忆/对话/规划）在云端；执行端是真架构成分，分两类。**

```
┌─────────────────────────── 云 ───────────────────────────┐
│  大脑 + 沙箱（规划/推理/代码都在这）                          │
│   · 推理出"该做什么" → 产出命令/计划                          │
│   · 云端任务直接在沙箱内跑（隔离，随时重建）                     │
└──────────────┬───────────────────────────────────────────┘
               │ 下发结果/命令（wss / MCP 双向通道）
               ▼
┌─ 执行端: 手机(termux)   /  盒子                ┌─ 渠道(飞书等)=耳朵/嘴
│  · 开一个"虚拟 MCP server" 承接云端命令          │  feed 同一个大脑
│  · termux = Linux 环境, 能装包/跑脚本/ADB
│  · 盒子常驻 = 任务宿主; 手机 = 移动执行
└───────────────────────────────────────────────
```

**核心动作链**（与"沙箱→命令→执行端"一致）：
1. 大脑在云的**沙箱**里规划/推理/写代码（隔离、可重建、不碰家庭真实环境）。
2. 沙箱跑完产出**命令/结果**。
3. 通过双向通道把命令**下发给执行端**执行（termux/盒子上的虚拟 MCP server 承接）。
4. 执行结果回传云，大脑继续。

| 维度 | 内存-执行端(手机/termux) | 盒子(常驻) |
|---|---|---|
| 角色 | 移动执行端 + UI | 常驻任务宿主机 |
| 能力 | 沙箱下发的命令本地执行、ADB、脚本、远程手 | 设备控制/定时/传感器/局域网文件/DAEMON |
| 在线性 | 不一定在线 | 长期在线 |
| 断网 | 只读缓存，待机 | 本地快照 + 基础自动化仍可跑 |

### 工具桥梁（Tool Bridge）
- 执行端 = **虚拟 MCP server**：向云注册（身份证书 + 能力清单），常驻 wss 保活。
- 云端工具（模型/检索/公共 API）在云上跑；家庭工具的调用经 MCP 路由到盒子/手机执行 → 结果回传大脑。
- 手机/盒子差异收敛为**可选性与优先级**：盒子优先，手机兜底。

### 身份双轨
- 家庭 = 云租户 = 一个大脑（人格隔离边界）。
- **人**（成员账号）= 人格身份，决定"谁在说"。
- **设备**（盒子/手机）= 执行身份，绑定家庭、持能力证书，决定"谁能执行什么"。

### 客户端形态（2026-09-01 落定）

**云侧 = Next.js（UI + SaaS 多租户）+ Go agent 内核，开在服务器。前端带 SaaS 是既定选择。**

用户拿到的"客户端"其实是**两个互不相识的独立部分**，不是"一个 App"：

| 用户手里的部分 | 本质 | 要装吗 |
|---|---|---|
| **UI 壳** | 云端 Next.js 的网页（浏览器 / WebView 都行，零代码） | **不用装**，任何设备浏览器打开即可 |
| **执行端** | termux 里跑的 **MCP server 进程**（收云端命令 / 本地执行 / 回传） | **可选装**：装盒子=家庭执行，装手机=移动执行 |

- **UI 不打包** —— 云端网页天然跨设备（手机/电脑/盒子大屏）。UI 侧不承载任何 SaaS 规则，只带 token 调云侧 API。
- **唯一要装的是执行端** —— termux + 一个 MCP server 二进制。它不叫"客户端"，是云的能力挂件：装了才有本地执行，不装也能纯聊天（沙箱在云端跑）。
- **封装 APK（webview + 内嵌执行端）** 纯粹是产品体验问题，不是架构问题；不封 = 网页聊天 + termux 装执行端，早鸟够用。

```
用户手机/盒子
  ├─ 网页/WebView ──→ 云端 Next.js（UI + SaaS 多租户） ──→│
  ├─ termux MCP server ──wss/MCP──→ 云端沙箱大脑(Go内核) ──→│ 大脑出一家人
  └─ 家庭设备 ──→ 云端渠道（飞书/音箱这些耳朵嘴）
```

执行端只认云端大脑、UI 只认云端网页，两边解耦——"前端带 SaaS"与"打包成啥壳"不冲突。

## 2. 记忆分层（解决"上下文有限"这个唯一硬约束）

AI 上下文窗口有限，一条上下文不可能无限积攒。分三层破解：

| 层 | 载体 | 职责 |
|---|---|---|
| **① 无界时间线** | per-tenant SQLite（append-only） | 全量长期记忆；聊天永不结束的真相来源；可渊源召回 |
| **② 工作上下文** | pi 引擎会话（滚动窗口） | 当前注意力：压缩后的最近消息 + 摘要 |
| **③ 每轮记忆快照** | 注入系统提示 | 把长期记忆压缩成"此刻该想起来的事"，喂进当前上下文 |

已有地基（v3 已建好，v5 沿用）：
- timeline-db / timeline-mirror：append-only 时间线 + 镜像
- pi 引擎 compaction：滚动窗口 + 摘要
- memory-extension / buildMemorySnapshot：每轮记忆快照

| # | 决策 | 说明 |

| 2 | owner 可空/多 owner | 空 = 家庭共享会话（群聊）；有 owner = 个人私有会话 |

### 3.1 会话 vs 身份对照

```
  ├─ 账号 mom / dad / kid（成员表）
  └─ sessions:

      mom-dm@web        ← mom 私有

```

## 5. 多租户 & 可扩展（已达成共识）

### 5.1 隔离层（v3 已完整）
per-tenant SQLite、per-tenant sessions 目录、per-tenant timeline、auth 绑定 tenantId。

### 5.2 容量：per-tenant SQLite + 粘性 worker 池（核心扩容路径）

> 决策（2026-09-02）：**HomeSense 不走 Postgres**。扩容路径是 **per-tenant SQLite + 粘性 worker 池 + LiteFS/S3 备份**。
> 理由与详细分析见 `v5/docs/scaling-strategy.md`。

#### 5.2.1 为什么是 SQLite 不是 Postgres

| 维度 | per-tenant SQLite | Postgres |
|---|---|---|
| 删租户 | `rm file.db`（物理隔离，无法泄漏） | `DROP SCHEMA`（有锁、有缓存、可能残留） |
| 跨租户查询 | ❌ 天然无（**HomeSense 永远不需要**） | ✅ |
| 单租户延迟 | 0 网络，本地文件 | 跨网连接池 |
| 写并发 | 单写者，但**租户之间不冲突** | 全局 MVCC |
| 运维 | 0（文件即一切） | pg_dump/wals/replica |
| GDPR/隐私 | **强**：物理隔离 | 弱：同盘同 schema |
| 单库成本 | $0 | 连接/IO/存储 |

HomeSense 是家庭场景，跨租户聚合**毫无业务价值**。Postgres 唯一赢的"跨家庭 BI"在 HomeSense 永远不存在。

#### 5.2.2 扩容模型

```
LB (粘性 hash(tenantId) % N)
  ├─ worker-1   持有 ten_a, ten_b, ten_c ...
  ├─ worker-2   持有 ten_d, ten_e ...
  └─ worker-N
       │
       └─ 每个 tenant 一个独立 .sqlite 文件
            WAL + 写锁 = 天然并发隔离
            读可走 LiteFS 只读副本
            写只走粘性路由到的那个 worker
```

#### 5.2.3 容量里程碑

| 形态 | 家庭数 | 并发聊天 | 关键点 |
|---|---|---|---|
| 1 worker | 50–200 | 100–400 | fd 上限（ulimit）、内存 |
| 4 worker 粘性分流 | 500–1500 | 1000–3000 | worker 数 = fd 上限 / 100 |
| 8 worker + 读副本 | 2000–5000 | 5000+ | LiteFS 只读分担读流量 |
| 16+ worker + LiteFS 跨机 | 10000+ | 20000+ | S3 备份，进程重启自拉回 |

> 真正贵的不是 SQLite，是 **pi agent 状态**。但 agent 状态本来就是 per-session 的，跟着 tenantId 走粘性就行。

#### 5.2.4 session 状态外置：不是"无状态"，是"按租户小有状态"

- 每个 worker 持有 N 个 per-tenant SQLite + N 个 pi agent session
- tenant 文件物理隔离，**删租户 = 删文件**
- 进程重启 = LiteFS 自动从 S3 拉回该 worker 持有的文件
- 状态在 worker 内存里，但**只要 worker 挂掉、它持有的租户粘性路由到别的 worker**（要么热迁，要么新 worker 拉文件 + 重建 session）

**不是解耦重写**，是给现有架构加一层粘性路由。worker 之间不需要共享内存。
