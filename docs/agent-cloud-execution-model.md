# agent 执行模型与安全定稿

> 状态：已定稿（2026-09-08）
> 范围：v7 多租户云脑 未来 agent 执行沙箱的架构决策
> 关联：old/v5/docs/tool-bridge-design.md（WSS 出站备选通道）、third_party/picoclaw/pkg/isolation（已废弃路线）

---

## 1. 结论一句话

**云大脑只负责"想"，本地才负责"动"**：云端永不运行租户的任意命令；所有需要真 shell / 真权限的动作，经服务端预演 + 分级审批后，落到用户自己设备上的 executor（真 shell、用户权限）执行。云仍承担核心云价值：智能规划、预演、审批、审计、定时、跨设备调度。

由此，云上"任意代码沙箱"档整体取消；被业界反复讨论的"每个租户一个内核/微VM"在代价上不可行且不需要。

---

## 2. 为什么画了这么多圈

### 2.1 现有 bwrap 沙箱的真相（已核实并废弃）
代码里确实有 `pkg/isolation`（bubblewrap 后端），但：
- 只有**静态单测**（断言 bwrap 参数串），从未真正起 bwrap 进程验证隔离行为
- 在 v7 产品流量中**从未启用**（config 默认关，exec/spawn/cron 全关）
- 实测（本机起 bwrap）：根是全新私有 root（写 `/` 不进宿主）、隐式 userns 意外挡住 setuid 提权与宿主文件读取；但 **无 `--unshare-net`（网络共享）、无 `--unshare-pid`（宿主进程可见）、env 全继承、无资源限制** —— **不构成安全边界**
- `isolation.Configure/CurrentConfig` 是全局单例 + 共享 instance root —— 多租户下会互相串，属缺陷

结论：**该沙箱未经过实践验证，按生产安全标准不达标**。作为"自定义脚本执行"的兜底与否，后续另行评估，不进入本期设计。

### 2.2 业界调研结论（2025-2026）
- 多租户跑 LLM 生成的不可信命令，**没人用进程级挂载做唯一防线**（"标准容器里，工作负载离宿主沦陷只有一个系统调用之遥"——gVisor 文档）
- 生产级底线是不共享内核：**gVisor**（用户态内核，CPU 5-15%，不可用 GPU）或 **Firecracker/Kata**（微VM，每租户 ~64-128MB 内存 + KVM 资源，125ms 启动）
- 硬化共享型容器（`--cap-drop=ALL --no-new-privileges` + 非 root + seccomp + cgroup + `--network=none`/白名单代理）只配**受信/受控工具**，不给任意命令
- 两家通用模式：
  - **网络**：执行沙箱默认无网/出网全走沙箱外部的白名单代理
  - **凭证**：密钥永不进沙箱——沙箱外代理持 token，只注入 scope 受限临时凭证（Claude Code 标准）

### 2.3 我们否掉了什么
| 方案 | 否掉原因 |
|---|---|
| 每租户一个内核（Firecracker/Kata/微VM） | 资源开销极大，完全不可行 |
| 共享内核 + 任意命令 | 必然弄死宿主/互连（唯一不可接受的组合） |
| "有沙箱才能叫 SaaS，所以云上必须跑任意代码" | 混淆了"云价值"和"命令执行位置"；云的竞争力在智能+编排+预演+审批+审计 |
| "全给客户端就完事" | 丧失云价值，退化为远程控制（本设计否决的另一个极端） |

## 3. 目标架构

```
                    ┌───────────────────────────────┐
                    │              云端 (v7 云大脑)     │
                    │                                │
  用户指令 ────────► │  Agent 推理 / 规划 / 多设备调度    │
                    │       │                        │
                    │       ▼                        │
                    │  预演 (dry-run, 语义级)          │
                    │   · 生成命令特征                 │
                    │   · 影响预览（读/写/网络/提权意图） │
                    │       │                        │
                    │       ▼                        │
                    │  信任策略引擎 (L0-L3 判档)        │
                    │       │                        │
                    │       ▼                        │
                    │  审批流 (冻结/通知/一次授权)       │
                    │       │                        │
                    │       ▼                        │
                    │  下发 <命令 + policy 标签>       │
                    └───────┬───────────────────────┘
                            │  MCP Streamable（Bearer 鉴权，已实现）
                            ▼
                    ┌───────────────────────────────┐
                    │       本地 executor (用户设备)     │
                    │                                │
                    │  受限 shell 前端:                │
                    │   · fixed cwd / timeout / 输出截断 │
                    │   · env 注入(不含云 secrets)      │
                    │   · 独立复核同一策略引擎(最后一道闸) │
                    │   · 真 shell + 用户权限执行        │
                    │   · stdout/stderr/exit 回传      │
                    └───────────────────────────────┘
```

- 双向走 MCP Streamable HTTP + Bearer token（已完成协议对齐与鉴权）
- 预演结果只是"预期影响 + 风险画像"，**结果真实与否由本地执行回传共同决定**，回传结果再驱动 agent 继续推理

## 4. 预演（dry-run）定位与边界

- **作用**：回答"这条命令会不会越界、语法是否成立、会碰什么"，而非"一定成功"
- **原因**：云环境 ≠ 本地环境（路径/设备/环境变量不同），云上不可能顶替本地真实结果
- **产物**：命令特征（命令名/参数域/路径域/网络域）+ 影响预览 + 建议信任档位

---

## 5. 信任梯度（审核与便利的调和）

| 档位 | 匹配条件 | 行为 | 延迟 |
|---|---|---|---|
| **L0 稳定白名单** | 命中最稳定已知模式（只读、查询类） | 直接放行，零审核 | 无感 |
| **L1 已验证模式** | 命中"曾经通过审核 + 获批并记住"的模式 | 自动放行（保留审计） | 无感 |
| **L2 探索** | 新命令/新参数域/写/网络/安装 | 冻结等审核（可跨端通知），通过后可选"记住" | 慢（可并行处理） |
| **L3 高危** | 提权/删宿主目录/敏感文件面 | 永不自动，单独二次确认 | 卡住 |

### 5.1 "批准并记住"机制
1. 稳定工作流首次执行落在 L2 → 人工审一次 → 勾选"此命令/此类命令记住"
2. 第二次起命中 L1 → 全程自动放行（与全权限体验一致，且每次留审计）
3. 新探索动作才回到 L2 慢审 —— 即"**稳定工作流直接放行，探索期慢慢审核**"

### 5.2 防该机制反噬的护栏（定死的规则）
1. **deny list 优先级最高**：命中提权/敏感面一律拦截，与是否被记住无关
2. **参数域越界降级**：记住的是模式结构（如 `adb shell <cmd>` 白名单参数域），运行时参数落进未知域 → 自动降级 L2，防 LLM 借用已被记住的壳跑恶意载荷
3. **记结构不记字面**：`git <action> <repo>` 形式而非长串命令，防 prompt injection 冒充已批准形态
4. **本地独立复核**：云判 auto 打标下发，本地 executor 以同一策略引擎副本复核一次（不信任单点）
5. **模式匹配可复用** v5 已有 `rule_engine`（精确匹配）与 `workflow_match`（指纹匹配）思路

---

## 6. 安全边界结论

- 云侧永不持有"任意命令执行权"；可信执行在用户自己的设备上，风险后果归属用户，云不放大
- 本地 shell 不是无防护：受限前端（timeout/cwd/env 注入/输出截断）+ 策略引擎本地副本 + L3 永不自动
- 视觉上仍然是完整 SaaS 云服务：能力卖点是**智能/编排/预演/审批/审计/定时/跨设备**

## 7. 本期 P0 实现清单

1. **工具面裁剪层**（云上游, 纯代码防御）：
   - 文件工具 canonical 路径校验（Clean + EvalSymlinks + workspace 前缀 + allow_dirs 白名单；禁 ../ 逃逸、symlink 逃逸）
   - 网络工具 URL 白名单 + SSRF 防护（禁私网/元数据/环回 + DNS rebinding 防护）
   - 每工具 JSON schema 参数强校验
   - per-tenant 配额（请求/并发/超时/workspace 磁盘限额）
2. **预演干-run**：命令特征 + 影响预览产出（复用于信任判档）
3. **信任策略引擎**：L0-L3 判档、模式库、deny list、参数域越界降级、"批准并记住"持久化
4. **下发/执行管线**：命令 + policy 标签下发；本地 executor 受限 shell 前端 + 本地策略副本复核 + 回传
5. **审批 UI/通知**：跨端审批触点（待审核项、影响预览展示、记住勾选）
