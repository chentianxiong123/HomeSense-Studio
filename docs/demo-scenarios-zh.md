# HomeSense Studio Plus 演示实验场景设计

> 文档定位：这不是测试用例清单，而是面向 GitHub 展示、B 站视频、作品集叙事的实验场景设计。
> 目标是让每个场景都能同时证明产品价值、系统能力和工程深度。

## 1. 设计原则

演示场景不能只是“能不能开个电视”。

一个好的演示场景应该同时具备：

1. 有人能马上理解的真实动机。
2. 能明显看出系统在做事，而不是假聊天。
3. 能展示多模块协作，而不是单一 API 调用。
4. 能讲出失败、恢复、记忆、编排这些高级能力。
5. 能在 GitHub README、录屏视频、面试讲解里复用。

因此场景设计按三层来做：

- `Hero Demo`：一眼记住项目是什么。
- `Capability Demo`：拆开证明系统核心能力。
- `Expansion Demo`：证明这个系统未来不是只能控电视。

## 2. 项目叙事主线

这个项目最适合的公开叙事不是“智能家居平台”，而是：

```text
一个家庭场景 Agent 操作系统。
它既能帮父母完成家庭娱乐控制，
也能让高级用户在 Studio 里把家庭和工作室自动化编排成流程。
```

对外讲述时建议分两条主线：

### 主线 A：父母/老人友好的家庭娱乐助手

强调：

- 自然语言。
- 少按钮。
- 少学习成本。
- 多设备联动。
- 失败可恢复。

### 主线 B：Studio Agent 中枢工作台

强调：

- 可视化工作流。
- 外部执行能力。
- 多 Agent 调度能力。
- 经验沉淀。
- 可重放、可调试、可编排。

这两条线合在一起，能让项目同时有“温度”和“技术含量”。

## 3. Hero Demo

### 场景 H1：一句话开始看电视

用户说：

```text
帮我打开东芝电视看机顶盒
```

系统表现：

- 识别“东芝电视”“机顶盒”。
- 规划开电视、开机顶盒、切信号源。
- 显示执行前预览。
- 执行动作并展示 Trace。
- 成功后写入 Experience。

为什么它是 Hero Demo：

- 一句话就能解释项目。
- 场景非常生活化。
- 有真实设备动作感。
- 能同时展示 Chat、Agent、设备层、Trace、Experience。

适合：

- GitHub README 首屏 GIF。
- B 站开场 15 秒。
- 面试里的第一段演示。

### 场景 H2：下次我只说“看电视”

用户第一次说：

```text
帮我打开东芝电视看机顶盒
```

第二次说：

```text
看电视
```

系统表现：

- 第一次走计划与执行。
- 第二次直接命中已编译的计划或已保存 Workflow。
- 路径更短，解释更简洁。

它证明的不是“又控制了一次电视”，而是：

- 经验写回。
- 编译知识层。
- L1/L2/L3 升级。
- 系统在学习，不只是一次性回答。

## 4. 家庭娱乐主线

### 场景 F1：给父母的一键观影模式

用户说：

```text
帮爸妈把电视打开，切到能看节目的状态
```

系统表现：

- 识别默认电视与默认机顶盒。
- 自动完成开机、切源、调到合适音量。
- 小爱播报一句确认。

证明点：

- 家庭上下文默认值。
- 人类导向的意图理解。
- 多设备联动。
- 中枢设备调用。

视频讲述点：

“这个项目不是给技术人玩的面板，而是把复杂控制压成一句话。”

### 场景 F2：模糊指代与家庭语境

用户说：

```text
把那个电视声音调大一点
```

系统表现：

- 结合最近上下文，判断“那个电视”是哪台电视。
- 调大音量。
- 在 Trace 里解释实体消歧依据。

证明点：

- 上下文补全。
- 家庭语境理解。
- 多设备消歧。

### 场景 F3：红外失败后的恢复

系统初始设置：

```text
小爱红外中枢第一次发按键失败
```

用户说：

```text
切到乐视电视
```

系统表现：

- 第一次红外操作失败。
- StateMachine 未观察到目标状态。
- CompensationService 重试。
- 第二次成功。
- Failure Trace 和恢复过程完整可见。

证明点：

- 系统不是 happy path demo。
- 有状态校验。
- 有失败补偿。
- 有可解释性。

这类场景对视频非常加分，因为“失败后恢复”比单纯成功更像真实系统。

### 场景 F4：打开台式机工作

用户说：

```text
帮我把台式机开起来
```

系统表现：

- 调用蓝牙开机卡。
- 台式机状态从 `off -> booting -> on`。
- 需要时触发后续工作流，比如播报“电脑已启动”。

证明点：

- 家庭娱乐之外还有生产力设备控制。
- 抽象层不是只为电视写的。
- 状态机设计是通用的。

## 5. Studio 主线

### 场景 S1：把“看电视”保存成 Workflow

用户先通过 Chat 完成一次“打开东芝电视看机顶盒”，然后说：

```text
把刚才的流程保存成工作流
```

系统表现：

- 从 Experience 生成 Workflow candidate。
- 在 Studio 里出现对应节点流程。
- 用户可手动编辑、重命名、再执行。

证明点：

- Chat 与 Studio 共用内核。
- Experience 可以晋升为 Workflow。
- Studio 不是孤立画布，而是系统的一部分。

### 场景 S2：工作流可视化调试

用户在 Studio 中点击运行“看电视”工作流。

系统表现：

- 节点逐步高亮。
- 每个节点的输入、输出、执行状态可见。
- 失败节点可定位。

证明点：

- Trace 是系统级能力。
- WorkflowRuntime 独立成立。
- 项目不是“LLM 黑盒”。

这类场景适合录一段静音 screen capture，配讲解非常清楚。

### 场景 S3：故事型自动化

用户做一个 Workflow：

```text
晚上回家
-> 播报一句欢迎语
-> 打开电视
-> 切到机顶盒
-> 调低音量
-> 打开笔记本相关工作提示
```

这个场景很适合视频，因为它开始有“编排感”和“仪式感”，能体现 Studio 的表达力。

证明点：

- Studio 是可讲故事的。
- 工作流不只是 if/else，而是生活流程建模。
- 未来可以自然扩到打印机、3D 打印机、工作室设备。

## 6. 扩展能力主线

### 场景 E1：B 站 CLI 作为外部执行能力

你提到 B 站 CLI，这个非常适合做“项目能力证明器”。

用户说：

```text
帮我把今天的项目进展整理成一条 B 站视频简介草稿
```

或者：

```text
把这个演示流程导出成一份适合发 B 站动态的文案
```

再进一步：

```text
调用 bstation-cli / bilibili-cli 生成草稿、上传封面、准备发布参数
```

证明点：

- 系统不依赖家庭设备才成立。
- CLIBridge + Skill + Workflow 的外部执行能力是通用的。
- 项目有“家庭操作系统”向“个人工作流操作系统”扩展的空间。

这个场景非常适合 GitHub，因为它让人立刻明白：这个系统不是只能控家电。

### 场景 E1.5：Studio 调度外部 Agent

用户在 Studio 中编一个工作流：

```text
整理今天的实验记录
-> 调用 Claude Code / Codex 总结实现进度
-> 调用 OpenClaw 或其他桌面 Agent 执行本地整理动作
-> 调用 B 站 CLI 生成发布草稿
```

系统表现：

- Workflow 不直接“自己做完所有事”，而是把外部 Agent 当成节点。
- 每个 Agent 节点都有输入、输出、状态和 Trace。
- 失败节点可以重试、替换执行器或人工接管。

证明点：

- Studio 是 Agent 中枢，不是单机设备控制台。
- 工作流节点可以是“另一个智能体”。
- 项目天然适合接更多执行器，而不只是米家和电视。

### 场景 E2：内容生产工作流

用户说：

```text
把今天的实验过程整理成一条公开视频脚本
```

系统表现：

- 汇总 Trace。
- 生成标题、简介、章节。
- 保存为 Markdown。
- 后续可交给外部 CLI 处理。

证明点：

- 系统能把内部运行数据转成外部内容产物。
- 编排能力不仅限于设备控制。
- Studio 和内容生产链路能联动。

### 场景 E3：未来工作室设备占位

虽然你家现在没有家庭打印机、3D 打印机，但可以用“虚拟工作室设备”做前瞻场景：

```text
把这个设计稿发到工作室打印机
开始打印一个 3D 样件
如果失败就发通知并保留任务
```

这个场景不建议现在优先实现，但非常适合写进 README 的“未来扩展能力”。

它的意义不在于立即落地，而在于说明：

- 现在的设备能力层不是为电视硬编码的。
- Workflow/ServiceRegistry 可以扩到更广的执行器。

## 7. 最适合先做的 6 个场景

如果我们只选最值得先实现、最值得先录视频的一批，我建议是：

1. `Hero`：一句话开始看电视。
2. `Learning`：第二次只说“看电视”直接命中已编译计划。
3. `Reliability`：红外失败后自动重试恢复。
4. `Context`：模糊指代“那个电视”也能正确执行。
5. `Studio`：把 Chat 成功路径保存成 Workflow 并在画布里重跑。
6. `Expansion`：调用 B 站 CLI 生成内容草稿或发布准备任务。

这 6 个场景组合起来，已经足够支撑：

- GitHub README 展示。
- 一个 3 到 8 分钟的视频。
- 面试里的完整讲述。

## 8. 视频结构建议

最适合的视频结构不是“按模块介绍”，而是按故事推进：

1. 开场一句话：帮我打开东芝电视看机顶盒。
2. 展示系统不是假聊天，而是真的执行。
3. 展示第二次说“看电视”更快。
4. 故意注入一次红外失败，展示恢复。
5. 切到 Studio，把流程保存成工作流。
6. 展示 B 站 CLI / 外部任务，证明它不是只能控家电。
7. 收尾：这是家庭场景 Agent + Studio 自动化工作台。

## 9. GitHub 展示建议

README 最适合突出这几件事：

- 一句话项目定义。
- 一张系统架构图。
- 一个 15 秒 Hero Demo GIF。
- 6 个能力场景卡片。
- 一个 Trace 截图。
- 一个 Studio 截图。
- 一段“为什么不只是智能家居”的说明。

## 10. 成功标准

这些演示场景设计成功的标志不是场景数量多，而是别人看完之后能立刻说出这几句话：

- 这是一个真的会执行的系统。
- 它不只是聊天，而是有状态、有记忆、有工作流。
- 它先解决父母看电视这种真实问题，再扩到更大的自动化空间。
- 它既能做家庭助手，也能做工作室自动化底座和 Agent 中枢。
